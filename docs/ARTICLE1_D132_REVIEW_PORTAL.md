# Article 1 / D-132 — private verifier portal

## Scope

PR-9 instantiates the reusable `HumanReviewEngine` for the first private Article 1 human-verification application.

The application assembly lives under:

```text
src/nutev/applications/willian_doctorate_a1/
```

The reusable review engine remains under:

```text
src/nutev/review/
```

No Article 1 behavior is added to the generic engine.

`D-132` is the private review protocol identifier in this application. PR-9 does **not** interpret the number `132` as a sample size.

## Sampling contract

Sampling is explicit and fail-closed.

### MANIFEST_EXACT

Default for `d132-v1`:

```text
use exactly every record in the canonical manifest
preserve the canonical record set
no implicit resampling
```

Current result: exactly 100 records.

### EXPLICIT_RECORD_IDS

Available for a future reviewed configuration:

```text
operator/scientific config provides every selected record_id explicitly
all IDs must exist in the source manifest
no duplicate ID
no unknown ID
source order is preserved before reviewer randomization
```

There is no hidden random sample-size algorithm in PR-9.

## Reviewer independence

D-132 v1 keeps the established two-reviewer contract:

```text
slot A
slot B
```

Both reviewers receive the **same record identities** but in deterministic different orders.

The ordering seeds reuse the existing Article 1 PRESS protocol:

```text
A -> first 16 hex chars of source_run_sha256
B -> next 16 hex chars of source_run_sha256
```

If the two permutations ever collide, B is deterministically rotated one position, matching the legacy packet-builder safety rule.

## Decisions

The application preserves the existing labels:

```text
Y = relevant
N = not relevant
U = uncertain; requires later abstract/full-text inspection
```

Rules:

```text
reason required
U is not converted to N
U does not become an automatic precision label
invalid labels fail
submit locks all reviewer decisions
```

D-132 does not fetch abstracts from the network. The existing canonical packet source is metadata-only; uncertainty remains `U` for a later authorized inspection step.

Current reviewer metadata:

```text

```

The D-132 config loader rejects blinded fields such as:

```text
r1_decision

score
nutev_rank
nutev_score
machine_relevance

```

The generic `HumanReviewEngine` applies the allowlist again when serializing the assignment payload.

Therefore blinding is backend-enforced rather than CSS-only.

## Project ownership gate

Knowing the D-132 endpoint is not sufficient.

Authenticated owner/admin/researcher operations require:

1. valid pilot session;
2. current workspace and project selected;
3. backend-confirmed access to that project;
4. active `ResearchApplication`;
5. `template_id = SCOPING_REVIEW`;
6. project configuration:

```json
{
  "assembly_id": "WILLIAN_DOCTORATE_A1",
  "d132_config_version": "d132-v1"
}
```

A different user's scoping-review project cannot attach itself to the Article 1 D-132 source merely by calling the route.

The first-party application configuration is migration/ownership state, not a global template default.

The real Willian/A1 ownership activation remains blocked until the PR-7 runtime dry-run is completed and reviewed.

## Guest link

Issuing a reviewer slot returns a private link once:

```text
/review-d132.html#token=<secret>
```

The raw token is generated by `HumanReviewEngine` and only its SHA-256 digest is stored.

Browser behavior:

1. read `#token` from the URL fragment;
2. keep the token only in a JavaScript in-memory variable;
3. immediately call `history.replaceState` to remove the fragment;
4. send the token only through:

```text
Authorization: Bearer <token>
```

The portal does not place the credential in:

```text
query string
localStorage
sessionStorage
IndexedDB
cookie
HTML
embedded script
```

After a refresh, the fragment is gone by design. The professor must reopen the original private link.

This is fail-closed behavior.

---

## Guest authorization freshness

Every guest operation re-resolves the bearer token through the review store:

```text
GET review payload
POST decision
POST submit
```

No `ReviewerAccess` authorization object is cached between requests.

Therefore:

```text
expired token -> immediate deny
revoked token -> immediate deny
manipulated token -> deny
wrong round/reviewer -> deny
```

---

## Adjudication

Adjudication cannot open until both reviewer slots have submitted and locked.

Agreement and conflict remain distinct.

A conflict may be adjudicated only by an authorized project role.

Original reviewer decisions are never overwritten.

`U` is a legitimate configured decision and is never mechanically converted during conflict resolution.

---

## Scientific non-effects

A D-132 review round does **not** automatically:

```text
record PRESS PASS
decide C4
authorize GF-10
freeze a query
execute formal search
create screening inclusion/exclusion
rewrite Registry data
change article_id
create PRISMA
```

These are deliberately reported as `false` in the owner summary.
